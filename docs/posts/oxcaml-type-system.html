2026-08-31 Snippets of OxCaml Modes

Having recently read through the paper on OxCaml, the basic idea of modes as qualifiers on types was simple enough to grasp. A mode is a combination of three axes of qualifiers that determine how many times a value can be used, if a value has only reference to it and if a value can live beyond the region it is defined in. It’s only after working through the paper by writing snippets of code and poking at the type system did that rules become clear. This is the first of two-part post on the paper, so hopefully reading it is a good introduction to OxCaml’s type system, a topic for the post after this.

This entire post is a markdown file with pieces of code interspersed with explanatory comments. Some of these pieces are as presented in the paper or their slightly modified versions while others have been generated with the help Claude. All code presented here have been tested with OxCaml compiler versions 5.2 and 5.4.

Uniqueness #

The paper describes a unique value as one which the type system guarantees to have only one reference and hence a memory location at which that value can be replaced by a new one. Section 2.1 shows the following example:

type 'a list = Nil | Cons of { hd : 'a; tl : 'a list }

let rec rev_append xs acc =
  match xs with
  | Nil -> acc
  | Cons x_xs ->
    let tl = x_xs.tl in
    rev_append tl (Cons (overwrite_ x_xs with { tl = acc }))

let reverse xs = rev_append xs Nil

Both 5.2 and 5.4 failed to compile the above. For OxCaml 5.2, the error is:

Error: The overwriting extension is disabled
       To enable it, pass the '-extension overwriting' flag

Alert Translcore: Overwrite not implemented.
Fatal error: exception File "parsing/location.ml", line 1124, characters 2-8: Assertion failed

In 5.4:

Alert Translcore: Overwrite not implemented.
>> Fatal error: Location.todo_overwrite_not_implemented
Fatal error: exception Misc.Fatal_error

If it had been/When it is implemented, overwrite_ should replace the list in the tl of each Cons record with Nil (at the start of the rev_append function) or the reversed Cons record accumulated so far, thus reusing the same memory location for x_xs rather than a new allocation. This can only be possible when the xs is unique; being overwritten does not affect any other value in the program.

Parts of Unique types #

A pair type is defined as follows:

# type ('a, 'b) pair = { fst : 'a; snd : 'b };;
type ('a, 'b) pair = { fst : 'a; snd : 'b; }

The keyword unique is used to mark types as unique. Now how would a pair type marked with the unique mode behave? Let’s look at the following snippet:

let process_unique_pair (pair @ unique) =
  let x @unique = pair.fst in
  let y @unique = pair.fst in

  let repair @unique = {fst = y ; snd = x} in
                                        ^
  This value is used here, but it is already being used as unique

  let x @unique = repair.fst in
  let y @unique = repair.snd in

  Printf.printf "x = %d, y = %d \\n" x y


let _ = process_unique_pair {fst = 5; snd = 8}

The OxCaml type checker reports an error (indicated by ^ above). The first y is a binding storing a reference to a unique value. In creating the repair record, fst = y uses up the unique value pair.fst. At snd = x, the type-checker figures out that x also refers to the same unique value and responds that a unique value or reference cannot be used up twice. Now if we were to replace the first y binding as:

let process_unique_pair (pair @ unique) =
  let x @unique = pair.fst in
  let y @unique = pair.snd in

  let repair @unique = {fst = y ; snd = x} in

  let x @unique = repair.fst in
  let y @unique = repair.snd in

  Printf.printf "x = %d, y = %d \\n" x y

let _ = process_unique_pair {fst = 5; snd = 8}

x = 8, y = 5

Now there are no complaints from the type-checker. The first x and y are bindings to unique values and used to construct a new unique record (a fresh allocation in memory) so here we have repair as a unique value with fields containing references to distinct unique values. The second set of x and y bindings shadow the first and flipped values get printed at the end.

Adding a second record construction without unique modes on the first as:

let process_unique_pair (pair @ unique) =
  let x @unique = pair.fst in
  let y @unique = pair.snd in

  let repair = {fst = y ; snd = x} in

  let x = repair.fst in
  let y = repair.fst in

  let repair' = {fst = x ; snd = y} in
                                 ^
  This value is used here, but it is already being used as unique

  let x @ unique = repair'.fst in
  let y @ unique = repair'.fst in

  Printf.printf "x = %d, y = %d total: %d \\n" x y (x + y)

let _ = process_unique_pair {fst = 5; snd = 8}

The type-checker complains that in constructing repair', y is being reused even though both repair and y = repair.fst are not marked as unique. Starting from the pair @ unique type input to process_unique_pair, the type-checker traces that repair.fst is pair.snd, a unique value, and the second set of x and y are two different bindings referring to one unique value and so cannot be reused to construct repair'.

Aliased parts of a unique pair #

The mode that marks a value as not unique is @aliased and shown in the following snippet:

# let process_parts_aliased (pair @ unique) =
    let x @aliased = pair.fst in
    let y @aliased = pair.fst in
    Printf.printf "Aliased: x = %d, y = %d\\n" x y

  let _ = process_parts_aliased {fst = 5; snd = 8}

  Aliased: x = 5, y = 5\n

The same unique value has been assigned to two different variables x and y, both marked as aliased meaning values which may have more than one reference. x and y both refer to pair.fst which is unique. But a sub-moding relation between aliased and unique allows unique values to be used as aliased which makes pair.fst not unique within the function and permits two references to it.

Taking an earlier example, repair’s fst field is used to create two unique values:

let process_unique_pair (pair @ unique) =
  let x @unique = pair.fst in
  let y @unique = pair.snd in

  let repair @unique = {fst = y ; snd = x} in

  let x @unique = repair.fst in
  let y @unique = repair.fst in

  Printf.printf "x = %d, y = %d total = %d \\n" x y (x + y)

let _ = process_unique_pair {fst = 5; snd = 8}

x = 8, y = 8 total = 16

The second set of x and y end up as bindings to the same unique value. Why does then this piece pass the type-checker? The only explanation is that the second set of x and y are being used as aliased values.

When types are not explicitly marked unique, they are marked as aliased by default. In the piece below,x, y, z and z' are treated as aliased values as:

let process_parts_pair (pair @ unique) =
  let x = pair.fst in
  let y = pair.snd in

  let z =  x in
  let z' = y in

  Printf.printf "Test: x = %d, y = %d\\n" x y;
  Printf.printf "Test: z = %d, z' = %d\\n" z z'

let _ = process_parts_pair {fst = 11; snd = 22}

x = 11, y = 22\n
z = 11, z' = 22\n

Both z and z' are references t aliased values x and y. So using x and y twice, once directly in the first printf statement and the second time via z, z' is possible. Modifying the function into:

let process_parts_pair (pair @ unique) =
  let x = pair.fst in
  let y = pair.snd in

  let z = x in
  let z' = y in

  process_unique_pair pair;

  Printf.printf "Test: x = %d, y = %d\\n" x y;
                                            ^
  Error: This value is used here,
       but it is part of a value that has already been used as unique

  Printf.printf "Test: x = %d, y = %d\\n" z z'

let _ = process_parts_pair {fst = 11; snd = 22}

The type error comes up because after process_unique_pair is called using the unique input pair, the unique components of pair, pair.fst and pair.fst are used. The type-checker determines that the components of a unique value has already been used and the associated aliased references, x, y referring to those same unique values cannot be used.

Affinity for Closures #

Closures are ubiquitous in functional programming. They are functions that capture values from the lexical region around them. Capturing a value stores it in the closure.

let with_unrestricted_closures =
  let xs : int list @ unique = [1;2;3;4;5] in
  let f = fun zs -> rev_append xs zs in
  let ys @ unique = f [6] in
  let zs @ unique = f [7] in

 print_endline "";
 List.iter (fun x -> Printf.printf "%d " x) ys;

 print_endline "";
 List.iter (fun x -> Printf.printf "%d " x) zs
Error: This value is used here,
       but it is defined as once and has already been used:
File "...", line 9, characters 20-21:
9 |   let ys @ unique = f [6] in

In with_unrestricted_closure, closure f captures a value of list @unique type and returns a unique reversed list. The two calls to f mean using the same unique value twice. The error is pointing to the inferred mode for f which is @once:

  let f @ once = fun zs -> rev_append xs zs in ...

The type-checker is hinting that closures that capture unique values can only be called @once. The mode determining the number of times a function or closure can be called is called affinity. An affine value can be called at most once.

# let with_restricted_closure =
    let xs_1: int list @ unique = [1;2;3;4;5] in
    let xs_2 : int list @ unique = [1;2;3;4;5] in
    let f = fun ls -> rev_append xs_1 ls in
    let ys = f [6] in
    Printf.printf "\\n";
    List.iter (fun x -> Printf.printf "%d " x) ys;
    let g @ once = fun ls -> rev_append xs_2 ls in
    let zs = g [7] in
    Printf.printf "\\n";
    List.iter (fun x -> Printf.printf "%d " x) zs;;

5 4 3 2 1 6
5 4 3 2 1 7

with_restricted_closure works by giving each closure (f, g) its own unique list to capture; g is marked with @ once to make explicit that it may only be called only one time.

The paper makes the following statements:

Unlike with uniqueness, affinity cannot be forgotten. Uniqueness is a statement about the past (a value has not been aliased); it is safe to forget this detail. In contrast, affinity is a statement about the future (a value cannot be aliased); forgetting it could potentially make memory reuse observable

A value that is currently unique only has one reference and using it as an aliased value does not affect it’s underlying mode. A value’s affinity is a guarantee about how it will be used in the future.

The sub-moding for affinity is many < once i.e. values or types marked many can be used once but a once value can never be used many times. With unique < aliased, the unique value can “forget” its uniqueness and be used as a value with possibly more than one reference. But a once affinity can never be forgotten because if it were, the sub-moding relation would be once < many - closures that capture unique values could be called repeatedly thus clashing with the restriction on the reuse of unique values.

A list type with aliased elements #

The paper defines modes as deep wherein the elements constituting type with a mode also have that same mode. But if this restriction were to be eased up, then for example, an'a list can give the list itself and its elements different modes.

# type 'a list_with_aliased_elts =
    Nil
    | Cons of { hd : 'a @@ aliased;
                tl : 'a list_with_aliased_elts };;

type 'a list_with_aliased_elts =
    Nil
  | Cons of { hd : 'a @@ aliased; tl : 'a list_with_aliased_elts; }

a_list_with_aliased_elts type marks hd with the @@ aliased field modality. The list itself can be @ unique while each element is @ aliased

The paper describes a type:

val graph_nodes : graph -> node aliased list @ unique

Fleshing out this type and related code is very helpful in seeing how a unique list with aliased nodes can result.

NOTE: The OxCaml Stdlib provides a Modes.Aliased.t wrapper that pins a value to aliased mode. Wrapping the element type lets us use a plain 'a list (and standard functions List.map/List.iter) instead of a custom type.

module Aliased : sig
  type 'a t = { aliased : 'a @@ aliased } [@@unboxed]
end

In the type definition above, the [@@unboxed] attribute tells the compiler to not put the type in a box or allocate a separate block on the heap to store the type. By definition, this is only possible for types which have only one constructor with one argument or a record with one field.

type node = { id : int;
              mutable neighbors : int list }

type graph = { nodes : node array }

let graph_nodes (g : graph) : node Modes.Aliased.t list @ unique =
  let rec loop i =
    if i >= Array.length g.nodes
    then []
    else
      { Modes.Aliased.aliased = g.nodes.(i) } :: loop (i + 1)
  in
  loop 0

let () =
  let g =
     { nodes =
        [| { id = 1; neighbors = [ 2; 3 ] }
         ; { id = 2; neighbors = [ 1 ; 3; 4] }
         ; { id = 3; neighbors = [ 1; 2; 4] }
         ; { id = 4; neighbors = [ 2 ; 3] }
        |]
    }
  in
  let ns @ unique = graph_nodes g in
  List.iter (fun (w : node Modes.Aliased.t) ->
      Printf.printf "\\n node: %d " w.aliased.id) ns;
      Printf.printf "\\n graph still has %d nodes\\n" (Array.length g.nodes)

Here the node type is annotated with Modes.Aliased.t. The unique list resulting from calling graph_nodes is itself unique even when it contains aliased nodes. Iterating through the list does not use up its values.

let rev_graph_nodes graph =
  let aliased_nodes @ unique = graph_nodes graph in
  let nodes : int list @ aliased =
     List.map (fun (w : node Modes.Aliased.t) -> w.aliased.id) aliased_nodes in
  let rev_nodes = List.rev nodes in
    Printf.printf "Nodes for the reversed graph:\\n";
    List.iter (fun x -> Printf.printf "%d " x) rev_nodes

let () =
  let g =
    { nodes =
        [| { id = 1; neighbors = [ 2; 3 ] }
         ; { id = 2; neighbors = [ 1 ; 3; 4] }
         ; { id = 3; neighbors = [ 1; 2; 4] }
         ; { id = 4; neighbors = [ 2 ; 3] }
        |]
    }
  in
  rev_graph_nodes g

With aliased_nodes as the @unique input, the nodes function maps the ids of aliased nodes and returns a list that is aliased because a list that does not contain explicitly unique values is aliased. This is a reversal of how unique values can be used as aliased or a unique constructor can contain individually aliased values. But a list constructed by iterating over a list of unique values cannot be unique itself.

Locality #

Another mode specification is locality which constrains values from leaving a region. The definition of a region is OCaml is important to understand before moving on.

Functional languages such as Haskell have a function named main that is the function from which execution begins. In OCaml, there is no such restriction. OCaml programs are laid out as a sequence of let bindings with those at the first or top level of the file being global bindings and others being local to the function within which they are defined.

The body of a function (created by a let binding) is a region. Creating the following function results in:

let bad () = let xs @ local = [1;2;3] in xs
Error: This value is "local"
       but is expected to be "local" to the parent region or "global"
       because it is a function return value.
       Hint: Use exclave_ to return a local value.

let xs @ local = creates a local region. All values should remain within it but here, the list escapes to the outer region for the bad () function.

Rewriting the above removes the type error:

# let rec length_local (xs : 'a list @ local) : int =
    match xs with
    | [] -> 0
    | _ :: tl -> 1 + length_local tl;;
val length_local : 'a list @ local -> int = <fun>
# let good () = let xs : int list @local = [1;2;3] in
        let n = length_local xs in n;;
val good : unit -> int = <fun>

(Note: In 5.2 and 5.4, List.length is not mode-polymorphic (val length : 'a list -> int, no @ local), so it can’t take a local list at all. This is why the length_local function has been added).

Borrowing and a sneaky attempt #

Taking the idea from the Rust programming language, the borrow_ constructor is used to write a borrow function where a unique value is copied locally, passed to f and a tuple result with the original unique value and the result of the local copy of x applied to f. Since the borrow creates a local value, after f returns or the region of the let result = f (borrow_ (x : 'a @ local)) function no longer exists, only one reference to the x : 'a unique remains.

The &x in the paper apparently stands for the actual borrow_ construct.

type 'a global = { g : 'a @@ global }
type 'a aliased = { a : 'a @@ aliased }

let borrow x f = let result = f (borrow_ (x : 'a @ local))
      in (x : 'a @ unique), { a = result }
let sneaky : int list @ unique -> (int list * int list aliased) @ unique =
  fun xs ->
    let global_xs : int list global @ unique = { g = xs } in
    let { g = ys}, { a = ys' } =
      borrow global_xs (fun { g = xs' } -> xs') in
    ys, { a = ys' }

The provided snippet does not type check for 5.2 but does return the following error for 5.4:

Error: This value is aliased
         because it is the field g (with some modality) of the record at file "sneaky.ml", line 10, characters 8-18.
       However, the highlighted expression is expected to be unique
         because it is an element of the tuple at file "sneaky.ml", line 12, characters 4-19
         which is expected to be unique.

xs is a unique value. The borrow construct copies xs to ys. The field g is global (the global before the @unique) and so aliased by definition. This means it is not guaranteed to be unique, even though the entire record is marked as unique. Since the value of g cannot be both unique and aliased, the error crops up.

Modes #

All of the examples shown until now involve modes where a mode μ is a triple (a,u,l) with an affinity a, a uniqueness u and a locality l.

(modes)         μ ::= (a, u, l)
(affinities)    a ::= many | once
(uniquenesses)  u ::= unique | aliased
(localities)    l ::= global | local

Each mode axis has an order among its two constituent elements with:

many < once unique < aliased global < local

When a mode element μ ≤ μ', a term at modeμ can always be used where μ' is expected but never the other way around. This relation had been described as sub-moding and has already been used to construct correct code in the examples shown in the previous sections.

The paper describes modes are ordered pointwise i.e. the entire mode is determined by the triple made up of combining the determined order of three axes. For μ ≤ μ' to be valid, the conjunction of a ≤ a' and u ≤ u' and l ≤ l' must be valid.

Some type-qualifier systems (like Walker’s) attach qualifiers to every type, including value types nested inside pairs and records. A working version of such a system with linear types is documented here. Such systems needs additional checks (see containment_check at the above link) to make sure that side conditions in rules for type formation with qualified types are met.

OxCaml’s calculus adds qualifiers only to computation types. Since value types do not have any qualifiers or modes, in order to modify parts of data structures to have a mode different from the mode for the entire structure - an aliased field inside an otherwiseunique record for example — the calculus introduces a box type □^ν τ to represent the modality ν. Taking the box as the structure with a mode, the mode of the box’s content along one or more axes is described by modalities acting on mode triples to describe or determine these axes.

The three modalities A, M and G are:

A(a, u, l) = (a, aliased, l)
M(a, u, l) = (many, u, l)
G(a, u, l) = (a, aliased, global)

The A or (@@aliased) modality forces uniqueness to aliased. The M or (@@many) forces affinity to many and the G modality forces both uniqueness to aliased and locality to global. In the borrow construct, in order to copy a unique value to a local value, it is imperative to ensure that the value to be copied cannot be global as a 'a global makes the value silently default to aliased. In sneaky, xs is deliberately wrapped in the ’a global type before being borrowed and that is why it fails.

In OxCaml syntax, all three modalities show up as @@-tagged, [@@unboxed] wrapper records — the same shapes already used earlier in this post:

type 'a aliased = { a : 'a @@ aliased } [@@unboxed]
type 'a many    = { m : 'a @@ many }    [@@unboxed]
type 'a global  = { g : 'a @@ global }  [@@unboxed]

The [@@unboxed] attribute used when defining a type has zero allocation at runtime since each type, 'a aliased, 'a many, 'a global is a record with exactly one field, a narrower case from the definition described in the graph_nodes section.

§3.2 Syntax #

Let’s go over the syntax of the mode calculus.

Contexts are ordered lists of bindings, each binding either giving a variable a type and mode, or marking it unusable once it’s been consumed (Γ, x : −):

Γ ::= ∅ | Γ, x : − | Γ, x : τ @ μ

Types consist of the unit type, sums, products, the box type from §3.1, a function type that records the mode of both its argument and its result (τ @ μ → τ @ μ), and a type for space credits, ♣, for in-place memory reuse:

τ ::= 1 | τ + τ | τ × τ | □^ν τ | τ @ μ → τ @ μ | ♣

The expression language is:

e ::= x | ()
      | inl e | inr e | (e, e)
      | λx. e | e e
      | let x = e in e
      | box_ν e | unbox_ν e
      | let (x, y, z) = e in e
      | case e { inl x → e; inr y → e }
      | reuse e in (e, e)
      | borrow x = e for y = e in e

x, (), inl e, inr e, (e, e), λx. e, e e, let x = e in e, case e { inl x → e; inr y → e } are standard functional programming syntax for variables, unit and pairs, abstractions, applications, let bindings and pattern matching via case. box_ν e introduces the modality ν in e and unbox_ν eliminates the same from e.

let (x, y, z) = e in e destructures a pair e into y and z and hands back the pair’s own space credit x. If the allocation for x is unique, it can be later spent by reuse x in (e, e) to allocate a fresh pair without a new allocation. borrow x = e1 for y = e2 in e3 is the formal core behind the borrow/borrow_ constructs used in earlier examples. The paper doesn’t give stack-allocated regions their own separate syntax at all; a region is just borrow _ = () for y = e1 in e2 with e1 bound in a fresh region denoted by e2.

Locks for Closures #

The lock Γ,🔒_μ governs what a closure of mode μ = (a₂,u₂,l₂) is allowed to capture from its surrounding scope. It’s defined by three equations over the (ordered-list) structure of contexts:

∅, 🔒_(a₂,u₂,l₂)  =  ∅

Γ, x : -, 🔒_(a₂,u₂,l₂)  =  Γ,🔒_(a₂,u₂,l₂), x : -

Γ, x : τ @ (a₁,u₁,l₁), 🔒_(a₂,u₂,l₂)  =
    ⎧ Γ,🔒_(a₂,u₂,l₂), x : τ @ (a₁, u₁ ∨ a₂†, l₂)   if a₁ ≤ a₂ and l₁ ≤ l₂
    ⎩ Γ,🔒_(a₂,u₂,l₂), x : -                          otherwise

using the dagger operation ONCE† := UNIQUE, MANY† := ALIASED.

Equation 1: locking an empty context #

The base case — nothing to lock over. A closure that captures no free variables at all (its body only references its own parameter) is a genuine, minimal instance: whatever the rest of the ambient top-level context contains is irrelevant, since none of it is threaded into f’s own typing.

# type ('a, 'b) pair = { fst : 'a; snd : 'b };;

Equation 2: an already-dead variable stays dead #

If x is already x : - (fully consumed) before a closure tries to capture it, the lock is a no-op on it — μ (the closure’s own mode) doesn’t even appear in the result. It doesn’t matter whether the closure is once or many, local or global: a dead variable stays dead no matter what kind of closure tries to reach for it.

# let id (x @ unique) = x;;
val id : 'a @ unique -> 'a = <fun>
# let func_with_closure_captures_used_value =
    let a : int @ unique = 100 in
    let _ = id a in

    let xs : int list = [11;21;31;41;51] in
    let f = fun zs -> rev_append xs [a; zs] in
    let ys : int list @ unique = f 6 in

    print_endline "";
    List.iter (fun x -> Printf.printf "%d " x) ys;;
Line 13, characters 37-38:
13 |     let f = fun zs -> rev_append xs [a; zs] in
                                          ^
Error: This value is used here, but it has already been used as unique:
Line 10, characters 15-16:
10 |     let _ = id a in
                    ^

id a forces a genuine @ unique use of a, consuming it (marking it a : -); f’s body then references the now-dead a again, and the lock (equation 2) can’t revive it, regardless of f’s own mode.

Equation 3: the general case #

The interesting case, split on whether a₁ ≤ a₂ and l₁ ≤ l₂ hold. The affinity relation a₁ ≤ a₂ needed for the guard, spelled out over the two affinities:

a₁ relation a₂
many ≤ once

§3.4 Joining Usages #

Contexts are ordered lists (Γ ::= ∅ | Γ,x:- | Γ,x:τ@μ), and the partial join operation + combines the usage two sub-terms make of the same starting context — used whenever a typing rule has more than one premise (LET, PAIR, APP, SPLIT, REUSE, BORROW), with one deliberate exception: CASE does not join, since match arms are mutually exclusive (see below).

Rule 2: a variable already dead stays dead through the join #

(Γ1, x:-) + (Γ2, x:-) = (Γ1+Γ2), x:-

Both sides of a real, both-execute construct (here, a pair) show x already dead. This is not the same as both sides independently, freshly consuming a live resource — that’s a double-use and is rejected outright, before joining even applies:

Rule 3/4 vs. OCaml’s match/case #

match’s branches are mutually exclusive — only one ever runs — so CASE is the one typing rule in Fig. 2 that does not join its premises’ contexts with +. Both branches simply get typed against the same, untouched starting context; there’s nothing to reconcile between them, because “arm 1 used y, arm 2 didn’t” never happens in a single execution — only one arm’s usage is ever real.

Rule 3/4 (the join proper) is instead for constructs where both sub-terms genuinely execute — pairs, applications, lets:

(Γ1, x:-) + (Γ2, x:τ@μ) = (Γ1+Γ2), x:τ@μ
(Γ1, x:τ@μ) + (Γ2, x:-) = (Γ1+Γ2), x:τ@μ

“one side uses x, the other doesn’t” combines to “the joined context just inherits whichever side’s requirement was real” (the untouched side, x : -, contributes nothing) — contrasted with rule 5, where both sides use x (aliased), forcing the combined requirement up to affinity MANY.

The SUB rule #

Γ1 ≥ Γ2      μ1 ≤ μ2
──────────────────────
Γ1 ⊢ e : τ @ μ1
Γ2 ⊢ e : τ @ μ2

Premise: Γ1 ⊢ e : τ @ μ1. Conclusion: Γ2 ⊢ e : τ @ μ2. Γ1 ≥ Γ2 means Γ1 is the more-consumed context (recall the context ordering: a dead binding x:- is ≥ any live one, and among live bindings a weaker mode like aliased is ≥ a tighter one like unique) — so the premise’s context is the poorer/more-restrictive one, and the conclusion’s is the richer one. This is ordinary weakening: a term that already type-checks under a stingier context certainly also type-checks under any richer context that context is a further-consumed version of, and independently, μ1 ≤ μ2 lets the claimed output mode be weakened too. In substitution terms: μ1 (the tighter mode) can always be used where μ2 (the looser mode) is expected, never the reverse — the same direction as ordinary subtyping, where the subtype substitutes for the supertype.

The same pattern holds on all three axes: μ1 (tighter) used as μ2 (weaker) always works; the reverse always fails.

BOX/UNBOX #

There is no dedicated box_v/unbox_v keyword in real OxCaml — grepping the actual lexer source for this switch (oxcaml-compiler.5.2.0minus31/parsing/lexer.mll) turns up only "overwrite_" and "borrow_" as special tokens, nothing for box/unbox. The real mechanism is ordinary record construction and field projection, using a field tagged with a modality (@@). "box_aliased" isn’t special syntax — it’s just an unbound name:

# let x = box_aliased (5 : int);;
Line 1, characters 8-19:
1 | let x = box_aliased (5 : int);;
            ^^^^^^^^^^^
Error: Unbound value box_aliased

The [@@unboxed] wrapper types for all three modalities — A, M, G. [@@unboxed] makes these genuinely zero-cost: no allocation, no indirection, purely compile-time bookkeeping, matching BOX/UNBOX in the abstract calculus exactly. Building {a = x} is box_A x; projecting z.a back out is unbox_A z.

# type 'a aliased = { a : 'a @@ aliased } [@@unboxed];;
type 'a aliased = { a : 'a @@ aliased; } [@@unboxed]

# type 'a many = { m : 'a @@ many } [@@unboxed];;
type 'a many = { m : 'a @@ many; } [@@unboxed]

# type 'a global = { g : 'a @@ global } [@@unboxed];;
type 'a global = { g : 'a @@ global; } [@@unboxed]

Plain @ mode ascription is not boxing — it keeps the exact same type, just re-asserting (weakening) the mode. BOX specifically changes the type, from τ to the box type (here, int list to int list aliased) — a genuinely different type you construct and destructure through, not just a re-labeling of the same value.

Everything below has to be nested inside one top-level let, not written as separate top-level lets referencing each other — a general fact about top-level bindings unrelated to box/unbox specifically (a top-level let becomes part of the module’s interface, so a later, separate top-level let referencing it gets conservatively downgraded to aliased, regardless of its originally declared mode):

BORROW: three distinct layers #

Easy to conflate, so worth separating explicitly:

  1. The real language primitive. borrow_ is a plain unary prefix operator, borrow_ x, taking one expression, nothing more. Confirmed directly from the real parser grammar (oxcaml-compiler.5.2.0minus31/parsing/parser.mly):

    BORROW simple_expr %prec below_HASH
    { Exp.borrow ~loc:(make_loc $sloc) $2 }

    There is no three-part borrow x = e1 for y = e2 in e3 surface syntax anywhere in the real language — borrow_ is the real, low-level equivalent of the paper’s Rust-style &x notation (the paper’s own commentary says &x “stands for the real borrow_ x”).

  2. The paper’s combinator. val borrow : 'a @ unique -> ('a @ local -> 'b) -> ('a * 'b aliased) @ unique. This is an ordinary library-level function built from borrow_ (layer 1), not a language construct of its own — exactly what our sneaky example (earlier in this document) already defines:

    let borrow x f = let result = f (borrow_ (x : 'a @ local))
      in (x : 'a @ unique), { a = result }

    borrow (ours to define) is the paper’s combinator; borrow_ (the keyword) is the one real primitive it’s built on.

  3. The formal calculus’s BORROW typing rule (Fig. 2): borrow x = e1 for y = e2 in e3, a three-part binder. This is a proof-facing abstraction the soundness argument reasons about — it has no direct surface-syntax counterpart at all. Per the paper’s own note, it does double duty representing plain stack regions too (borrow _ = () for y = e1 in e2), which is likely why it’s shaped as a three-part binder in the calculus even though only the simple unary form (layer 1) made it into the real language.

Algorithmic VAR rule (§3.7): accumulated locks #

A variable captured through several nested lambdas accumulates one lock per nesting level in the context (Γ ::= ... | Γ,🔒_μ), and only when it’s actually referenced does VAR sweep up all the intervening locks at once:

a1 ≤ (a2 ∧ ⋀_(🔒_(ai,...)∈Γ') ai)
u1 ∨ ⋁_(🔒_(ai,...)∈Γ') †(ai) ≤ u2
l1 ≤ (l2 ∧ ⋀_(🔒_(...,li)∈Γ') li)

Affinity. The first inequality’s RHS is a meet (∧) over a2 and every intervening lock’s own affinity. On the two-element chain MANY < ONCE, the meet of several values collapses to MANY the instant any one of them is MANY — there’s nothing below MANY for the others to pull it down to. So a1 ≤ MANY forces a1 = MANY exactly, regardless of how many of the other terms were ONCE.

once_val is captured by inner (@ once — perfectly compatible on its own), which is itself nested inside outer (@ many). Even though inner alone would be fine, outer’s many propagates through inner’s own once and still collapses the meet — once_val gets rejected specifically because of outer, not because of inner. The error even blames once_val directly and points at outer’s whole body as the source of the conflict:

    outer ();;

         because it is used inside the function at lines 3-5, characters 23-14

Uniqueness. The second inequality is the exact mirror on the join side. ALIASED is the top of the uniqueness axis, so the join collapses to ALIASED the instant a single †(ai) is ALIASED — which happens the moment a single ai = MANY appears anywhere in the chain (MANY† := ALIASED), regardless of u1 itself or any other ONCE locks (ONCE† = UNIQUE, the bottom — joining with the bottom is identity, contributes nothing to pull it up). Appendix B: Mode Inference #

Everything from here on is about the paper’s inference algorithm — how the compiler actually solves for the modes it doesn’t require you to write down — rather than surface OCaml syntax. Most of this section has no corresponding compiler behavior to verify; it’s documentation connecting the paper’s own notation to the concrete examples already built and verified above.

Inference variables and positive/negative mode expressions #

Mode expressions get extended with inference variables (α), both for whole triples and for each individual axis:

μ ::= (a,u,l) | α
a ::= MANY | ONCE | α
u ::= UNIQUE | ALIASED | α
l ::= GLOBAL | LOCAL | α

Positive mode expressions (a⁺,u⁺,l⁺) and negative mode expressions (a⁻,u⁻,l⁻) are defined per axis:

a⁺ ::= a | a⁺ ∨ a⁺ | †⁻¹(u⁻)      a⁻ ::= a | a⁻ ∧ a⁻
u⁺ ::= u | u⁺ ∨ u⁺ | †(a⁻)        u⁻ ::= u | u⁻ ∧ u⁻
l⁺ ::= l | l⁺ ∨ l⁺                l⁻ ::= l | l⁻ ∧ l⁻

Positive expressions extend with join (∨); negative expressions extend with meet (∧). The solver accepts constraints of the shapes a⁺≤a⁻, u⁺≤u⁻, l⁺≤l⁻, μ⁺≤μ⁻, μ=μ, and solving them is “essentially just transitive closure” (the paper’s own phrase).

Crucially, this grammar isn’t evaluating anything — it’s a recursive syntax for expressions that may still contain unresolved α’s, built up symbolically during constraint generation and only collapsed once the solver has pinned every atom down. This is exactly why the accumulated-locks machinery in the algorithmic VAR rule (already verified concretely above) works the way it does: ⋀ aᵢ is an a⁻ expression; u₁ ∨ ⋁ †(aᵢ) is a u⁺ expression built from dagger applied to a⁻ atoms; l₁ ≤ (l₂ ∧ ⋀ lᵢ) is an l⁻ expression.

Once every atom in a chain resolves to a concrete value, the collapse is purely a fact about how join/meet behave on each axis’s two-element chain (MANY<ONCE, UNIQUE<ALIASED, GLOBAL<LOCAL), regardless of how deeply or in what order the expression was built — meet/join are associative, so only “does any atom hit the relevant extreme” (join) or “do all atoms avoid it” (meet) matters, never the tree shape:

Meet (negative expressions — collapses toward the axis minimum):

expression collapses to
a⁻ = a₁∧a₂∧... MANY the instant any aᵢ=MANY, ONCE only if every aᵢ=ONCE (verified: wrapper vs. wrapper_no_many)
u⁻ = u₁∧u₂∧... UNIQUE the instant any uᵢ=UNIQUE, ALIASED only if every uᵢ=ALIASED (not directly exercised above — there, the accumulated uniqueness chain landed on u⁺/join, not u⁻/meet)
l⁻ = l₁∧l₂∧... GLOBAL the instant any lᵢ=GLOBAL, LOCAL only if every lᵢ=LOCAL (verified: wrapper_local_chain vs. wrapper_local_chain_no_global)

Join (positive expressions — collapses toward the axis maximum):

expression collapses to
a⁺ = a₁∨a₂∨... ONCE the instant any aᵢ=ONCE, MANY only if every aᵢ=MANY
u⁺ = u₁∨u₂∨... ALIASED the instant any uᵢ=ALIASED, UNIQUE only if every uᵢ=UNIQUE (verified: wrapper_unique_chain vs. wrapper_unique_chain_no_many — precisely u₁ ∨ ⋁ †(aᵢ) ≤ u₂ collapsing to ALIASED the moment a single aᵢ=MANY feeds †(MANY)=ALIASED into the join)
l⁺ = l₁∨l₂∨... LOCAL the instant any lᵢ=LOCAL, GLOBAL only if every lᵢ=GLOBAL

Negative = meet = pulls toward “safer to assume less of” (the axis minimum). Positive = join = pulls toward “safer to assume more of” (the axis maximum). Every chain example already verified in this document lands cleanly into one of these six slots.

μ vs. u. Easy to misread as the same letter, but they are unrelated symbols. μ (the whole triple, μ ::= (a,u,l) | α) and u (the uniqueness axis alone, u ::= UNIQUE | ALIASED | α) range over different things — a mode triple vs. one component of it. So μ⁺≤μ⁻ is not a duplicate of u⁺≤u⁻; they aren’t even about the same kind of object. μ⁺≤μ⁻ is the whole-triple form of the constraint, used when a mode variable α hasn’t been decomposed into its three per-axis pieces yet; a⁺≤a⁻, u⁺≤u⁻, l⁺≤l⁻ are the per-axis forms, used once it has. The solver needs both shapes because inference sometimes generates a constraint on an entire undecomposed mode (e.g. from SUB’s μ₁≤μ₂) and sometimes on a single axis (e.g. from VAR’s three separate inequalities, already verified above).

For a⁺≤a⁻ specifically (MANY<ONCE), the satisfiable pairs are:

a⁺ a⁻ holds?
MANY MANY ✓
MANY ONCE ✓
ONCE ONCE ✓
ONCE MANY ✗

a⁺ accumulates a lower bound (join of every “must be at least this” requirement on the variable); a⁻ accumulates an upper bound (meet of every “must be at most this” requirement). a⁺≤a⁻ is the check that a value satisfying both actually exists — if the accumulated lower bound ever exceeded the accumulated upper bound, the requirements would be contradictory (“crossed”), which is exactly a mode error. Same reading applies pointwise to u⁺≤u⁻ and l⁺≤l⁻, and to μ⁺≤μ⁻ over whole triples.

Solving by transitive closure #

Why “solving is essentially just transitive closure” is literally true, worked out on a compound example. The splitting rules: join is a least upper bound and meet a greatest lower bound, so (in any lattice, nothing specific to this one):

X ∨ Y ≤ Z   iff   X ≤ Z  and  Y ≤ Z
W ≤ Y ∧ Z   iff   W ≤ Y  and  W ≤ Z

Applying both repeatedly, an n-way join on the left of a⁺≤a⁻ against an m-way meet on the right splits into the full n×m cross product of atomic pairwise constraints. Concretely, take:

(MANY ∨ (α₁ ∨ α₂))⁺ ≤ (α₃ ∧ α₄) ∧ α₅

Flattened by associativity the left has 3 leaves (MANY, α₁, α₂), the right has 3 (α₃, α₄, α₅), so this one compound constraint splits into 3×3 = 9 atomic constraints:

MANY <= α₃   MANY <= α₄   MANY <= α₅
α₁   <= α₃   α₁   <= α₄   α₁   <= α₅
α₂   <= α₃   α₂   <= α₄   α₂   <= α₅

MANY is the axis minimum, so the whole top row (MANY≤anything) is trivially true no matter what α₃/α₄/α₅ resolve to — those 3 edges carry no information and can be dropped. (Had the atom been ONCE instead, ONCE≤x would force x=ONCE for each — not vacuous.) Recursing this split on any leaf that is itself still compound eventually bottoms every constraint out at a genuine atom-to-atom or atom-to-variable edge; solving is then: build the graph of these ≤ edges, take its transitive closure (x≤y, y≤z ⟹ x≤z), and reject if any edge/path forces a value below the axis minimum above the axis maximum (e.g. a path forcing ONCE≤MANY).

The shared-node reading of α. It’s tempting to think a bare α appearing as a leaf of some a⁺ could just be an a⁻ expression in place — e.g. rewriting a leaf α to α₃∧α₄ directly inside the a⁺ tree above. That’s not a legal grammar substitution: a⁺ ::= a | a⁺ ∨ a⁺ | †⁻¹(u⁻) and a⁻ ::= a | a⁻ ∧ a⁻ share no same-axis production letting a⁻ sit inside a⁺ (only the dagger crosses axes — affinity a⁺ can embed a uniqueness u⁻ — never polarity on the same axis).

What’s really going on when the same α shows up on both sides of the whole constraint set (not within one constraint’s own tree) is a shared graph node linking two separate atomic constraints, e.g.:

C1:  β⁺ ≤ α        (something is a lower bound on α)
C2:  α  ≤ γ⁻        (α is a lower bound feeding γ⁻)

Transitive closure composes C1 and C2 through the shared node α into a new derived edge:

C3:  β⁺ ≤ γ⁻

α never “becomes” positive or negative depending on which side it’s written on — it’s one node with edges pointing in (from C1) and out (to C2), and closure is exactly: if an edge points in and an edge points out, add the direct edge across. That’s substitution-by-closure (propagating a resolved bound through a shared variable across separate constraints), not substitution-by-grammar (which the a⁺/a⁻ BNF does not allow).

A small real, compiler-verified instance of the C1/C2 ⟹ C3 chain above, on the uniqueness axis (UNIQUE < ALIASED). mid is left unannotated: it is the shared inference variable α, a bridge between a producer site and a consumer site.

  • C1 (edge into α): producer’s own fixed mode is @ unique — that is β⁺ ≤ α with β⁺ = UNIQUE.
  • C2 (edge out of α): consumer demands @ aliased — that is α ≤ γ⁻ with γ⁻ = ALIASED.

Closure chains these into the derived fact β⁺ ≤ γ⁻, i.e. UNIQUE ≤ ALIASED — true (this is the axis’s own order), so nothing α itself resolves to in between can break it:

Context splitting #

Context splitting is the operation dual to context joining (+, Section 3.4). Figure 2’s declarative rules pick premise contexts Γ₁,Γ₂ nondeterministically (“choose any Γ₁,Γ₂ with Γ₁+Γ₂=Γ”) — an existential guess, fine for a soundness argument, useless for an algorithm. Appendix B replaces the guess with a direct computation, parameterised by the free variables of the two subterms actually being checked:

⅄₍X,Y₎(Γ) = Γ_X + Γ_Y

X and Y are not arbitrary labels for “context one” / “context two” — they are literally FV(e1) and FV(e2) for whichever two subterms a rule is about to check separately. Γ_X keeps Γ’s bindings only for variables in X (blanking the rest to x:-, and likewise for Γ_Y). This is what makes the split deterministic and provably correct rather than a search: if x ∉ FV(e2), e2 syntactically cannot reference x, full stop — no evaluation, no guessing needed to justify marking it x:- on that side.

The six defining equations, and their pairing with the five + equations from Section 3.4 (page 253:10):

  • A: ⅄(∅) = ∅+∅ ↔︎ J1: ∅+∅ = ∅ — trivial, self-inverse both directions.
  • B: ⅄(Γ,🔒μ) = Γ_X,🔒μ + Γ_Y,🔒μ ↔︎ (no counterpart in J1..J5). Locks are not part of context syntax where + was defined (Section 3.4) — they only enter the grammar later, in Section 3.7’s algorithmic Γ ::= ∅ | Γ,x:- | Γ,x:τ@μ | Γ,🔒μ. So B isn’t inverting a published join rule; it’s pure structural duplication (a lock is copied unchanged to both sides, nothing is divided between two subterms), forced by the extended syntax rather than mirroring an existing case.
  • C: ⅄(Γ,x:-) = Γ_X,x:- + Γ_Y,x:- ↔︎ J2: (Γ1,x:-)+(Γ2,x:-) = (Γ1+Γ2),x:- — honest inverse: unused stays unused either direction, no choice, nothing lost.
  • D: ⅄(Γ,x:τ@μ) = Γ_X,x:τ@μ + Γ_Y,x:- where x∈X, x∉Y ↔︎ J3: (Γ1,x:τ@μ)+(Γ2,x:-) = (Γ1+Γ2),x:τ@μ — honest inverse: J3 absorbs a real usage and a - into the real usage; D hands the real usage back to the side that actually needs it (X, since x∈FV(e1)) and marks the other -.
  • E: ⅄(Γ,x:τ@μ) = Γ_X,x:- + Γ_Y,x:τ@μ where x∉X, x∈Y ↔︎ J4: symmetric mirror of J3/D.
  • F: ⅄(Γ,x:τ@(a,u,l)) = Γ_X,x:τ@(a,aliased,l) + Γ_Y,x:τ@(a,aliased,l) where a≤many, x∈X, x∈Y ↔︎ J5: (Γ1,x:τ@(_,aliased,l))+(Γ2,x:τ@(_,aliased,l)) = (Γ1+Γ2),x:τ@(many,_,l) — the interesting pairing, not a literal mirror: J5 requires aliased on both inputs and produces many affinity on the output. F requires a≤many on input (many is the axis minimum, so a≤many literally forces a=many) and produces aliased on both output copies. F’s precondition is exactly what J5 guarantees as output; F’s output is exactly what J5 needs as input — they invert each other end-to-end, built from opposite directions, which is exactly why a variable needed by both subterms at once (F) can only ever be handed out as two aliased copies: uniqueness cannot be duplicated, aliased can.

Which Figure 2 rules actually need ⅄ (i.e. have ≥2 premises typing different subterms, combined via +): APP, PAIR, SPLIT, LET, CASE, REUSE, BORROW. Everything else (VAR, SUB, LAM, UNIT, INL, INR, BOX, UNBOX) has 0 or 1 premise, so there’s nothing to divide between sub-derivations. CASE is a partial case even within that list: it needs only one split (Γ1 for the scrutinee e1 vs. Γ2 for the branches), not a three-way split like REUSE/BORROW, because the two branches e2/e3 deliberately share Γ2 rather than dividing it — only one branch ever runs, so there’s no simultaneous-access/aliasing concern the way there is when both sides of a PAIR genuinely run at once.

A loose thread worth flagging explicitly: x:- is overloaded across two different layers of the paper, and they are not the same fact.

  • Context - (everything above, and all of Section 3.4/Appendix B): static. “This subterm has no free occurrence of x.” The binding is still alive elsewhere in Γ; it’s just structurally absent from this particular piece of syntax. Known before any evaluation, purely from FV(e).
  • Store - (Section 4, page 253:13, μ̂ ::= μ | -): dynamic. “This binding was accessed at a mode requiring exclusivity and is now consumed.” Only knowable by tracking what evaluation has actually done so far; this is the mechanism that catches a UNIQUE value being read twice.

Same three-character notation, two unrelated mechanisms — one a static absence fixed by which variables a subterm mentions, the other a dynamic depletion fixed by evaluation order.

Figure 12: syntax-directed BOX/UNBOX per modality #

Figure 12 (page 253:51) specializes Figure 2’s generic BOX/UNBOX rule to the three concrete modalities A, M, G:

BOX:   Γ⊢e:τ@ν(μ)    ⟹  Γ⊢box_ν e:□^ν τ@μ
UNBOX: Γ⊢e:□^ν τ@μ   ⟹  Γ⊢unbox_ν e:τ@ν(μ)

where the modalities (Figure 1, page 253:9) are:

A(a,u,l) = (a, ALIASED, l)
M(a,u,l) = (MANY, u, l)
G(a,u,l) = (a, ALIASED, GLOBAL)

Applied literally these would force fixed values everywhere ν(μ) touches an axis. Figure 12 instead shows several of those positions as free variables — that’s submoding (SUB) silently folded in, per Appendix B’s stated design (“we resolve issue (2) by integrating submoding directly into carefully chosen other rules”, page 253:48). Every axis slot in every rule below is exactly one of three things:

M-box
  Γ⊢e : τ @ (MANY, u, l)            MANY: e must genuinely be many-affinity
  Γ⊢box_M e : □ᴹτ @ (a, u, l)       a: free — claim any affinity for the box itself
                                    u, l: unchanged, just carried through

M-unbox
  Γ⊢e : □ᴹτ @ (a1, u, l)            a1: free — the box's own claimed affinity is irrelevant
  Γ⊢unbox_M e : τ @ (a2, u, l)      a2: free — content was many, so weakening to anything is safe
                                    u, l: unchanged, just carried through

A-box
  Γ⊢e : τ @ (a, u1, l)              u1: free — any uniqueness weakens up to aliased
  Γ⊢box_A e : □ᴬτ @ (a, u2, l)      u2: free — claim any uniqueness for the box itself
                                    a, l: unchanged, just carried through

A-unbox
  Γ⊢e : □ᴬτ @ (a, u, l)             u: free — the box's own claimed uniqueness is irrelevant
  Γ⊢unbox_A e : τ @ (a, ALIASED, l) ALIASED: fixed — it's already the ceiling, nowhere higher to weaken to
                                    a, l: unchanged, just carried through

G-box
  Γ⊢e : τ @ (a, u1, GLOBAL)         u1: free (same as A-box)
                                    GLOBAL: e must genuinely be global
  Γ⊢box_G e : □ᴳτ @ (a, u2, l)      u2, l: both free — box's own claims are irrelevant
                                    a: unchanged

G-unbox
  Γ⊢e : □ᴳτ @ (a, u, l1)            u, l1: both free — box's own claims are irrelevant
  Γ⊢unbox_G e : τ @ (a, ALIASED, l2) ALIASED: fixed (same as A-unbox)
                                    l2: free — content was global, weakening to anything is safe
                                    a: unchanged

One rule of thumb covers every free/fixed choice above: a modality-controlled slot is free on the premise (BOX) side exactly when the modality forces the maximum of that axis (ALIASED is uniqueness’s ceiling — any input weakens up to it); it’s free on the conclusion (UNBOX) side exactly when the modality forces the minimum (MANY/GLOBAL are the floors — a produced value there weakens up to any claim). Wrong extreme → pinned to the literal constant instead. This is fully verified against Figure 1’s own minimum/maximum/modality columns: affinity min=MANY matches M’s forced value, so M is premise-pinned/conclusion-free; uniqueness max=ALIASED matches A’s and G’s forced value, so both are premise-free/conclusion-pinned on that axis; locality min=GLOBAL matches G’s forced value there too, so G is also premise-pinned/conclusion-free on locality.

And any slot that is the box’s own declared mode on an axis the modality doesn’t even read (the box’s own affinity in M-box/ M-unbox, its own uniqueness in A-box/A-unbox, its own uniqueness and locality in G-box/G-unbox) is simply always free — nothing to do with weakening at all, since the modality’s formula never consults that component of μ in the first place, exactly as in the fully generic Figure 2 BOX/UNBOX rule before any specialization.

Section 4: Usage-Aware Store Semantics #

The access-splitting rule #

The store only changes a binding’s mode when accessing it at some requested mode μ2: it splits the existing μ̂ into μ̂1 + μ2 and keeps μ̂1 in the store. The paper’s own phrasing (“split μ̂ into μ̂1 + μ2”) puts the original on the left, which is the clearer way to read it even though the paper prints the instance with μ̂ on the right:

(many, u, l) = (many, aliased, l) + (a, aliased, l)

Only two outcomes exist here, not three:

  • μ̂1 = (many, aliased, l): kept in the store. This is “the new mode of the binding” — one fact, not two separate ones.
  • μ2 = (a, aliased, l): granted to this one access only. Never written back anywhere — ephemeral, used for this single evaluation step and then discarded.

(many, u, l) is the mode sitting in the store before the access. Accessing at uniqueness ALIASED (any affinity a the accessor wants) is only legal if the store’s affinity is already MANY — matching the earlier M-modality reasoning: handing out a second (aliased) view of something is only sound if it was reusable to begin with. The free u on the left says the original binding could have started as either UNIQUE or ALIASED — doesn’t matter which, because the instant an aliased view is handed out, the retained copy is forced to ALIASED from then on regardless of what it was.

Why the granted a stays free instead of being forced to many. It’s tempting to think a many-affinity store binding can’t hand out a once-affinity view “at the same time” as being aliased, but affinity and uniqueness are orthogonal, tracking different things.

  • Affinity constrains what the recipient of this one access promises about that reference’s own future use. ONCE means “whoever holds this reference will use it at most once going forward” — it says nothing about the store’s own lifetime or how many other aliases exist.
  • Uniqueness is separate: ALIASED just means other simultaneous references might exist; it says nothing about how many times any particular one of them gets used.

So (once, aliased, l) isn’t contradictory: a reference that might not be the sole one in existence, and will be consumed at most once by whoever is holding it. Nothing stops an ordinary, already-shareable value from being fed into a single-use consumer (e.g. handed to a closure that is only ever called once) — that’s an everyday weakening, the same fact already seen for M-unbox’s free a2: MANY is the affinity axis’s minimum, so it can always be weakened up to anything, ONCE included, with zero risk, since MANY never promised more than one use, only permitted it. Forcing the granted a to stay MANY would be a real loss of expressiveness — it would make it impossible to ever hand out a single-use view of an ordinarily-reusable value. The store’s retained μ̂1 keeps its own MANY bookkeeping regardless, for future accesses; the granted view’s affinity is a separate, independent commitment about that one reference alone.

All eight instances #

Left of = is the mode already sitting in the store; right is the split: (kept in the store) + (granted to/consumed by this one access).

(many, u=UNIQUE,  l) at ALIASED = (many, aliased, l) + (a, aliased, l)
(many, u=ALIASED, l) at ALIASED = (many, aliased, l) + (a, aliased, l)
(many, u=UNIQUE,  l) at UNIQUE  = -                  + (many, unique, l)
(many, u=ALIASED, l) at UNIQUE  = stuck

(once, u=UNIQUE,  l) at ALIASED = -                  + (once, unique, l)
(once, u=ALIASED, l) at ALIASED = -                  + (once, aliased, l)
(once, u=UNIQUE,  l) at UNIQUE  = -                  + (once, unique, l)
(once, u=ALIASED, l) at UNIQUE  = stuck

Two independent triggers force the right column to - (full consumption, nothing kept): requesting UNIQUE access, or the store already being ONCE-affinity — either one alone is enough, which is why 6 of the 8 rows fall into it. Stuck is reserved for exactly one condition, independent of affinity: requesting UNIQUE against a store that is already ALIASED. Every other combination (both ALIASED-access rows on a MANY-affinity store) is the only place a genuine partial split — something kept, something granted, neither being - — actually occurs.

Figure 3: the full reduction relation #

The complete small-step semantics, page 253:15. Machine state: S ∥ E ▷^μ_n e — a store S, an evaluation context E (a zipper), the current mode μ, and a stack-frame counter n.

Value construction. unit, inl, inr, pair, box, lam are all the exact same shape: allocate a fresh address d in the current frame n, tagged with the current mode μ, holding the constructed value; evaluation continues at d, same μ, same n:

(unit) S ∥ E ▷^μ_n ()          ⇝ S,d↦^μ_n () ∥ E ▷^μ_n d
(inl)  S ∥ E ▷^μ_n inl b       ⇝ S,d↦^μ_n inl b ∥ E ▷^μ_n d
(inr)  S ∥ E ▷^μ_n inr b       ⇝ S,d↦^μ_n inr b ∥ E ▷^μ_n d
(pair) S ∥ E ▷^μ_n (b,c)       ⇝ S,d↦^μ_n (b,c) ∥ E ▷^μ_n d
(box)  S ∥ E ▷^μ_n box_ν b     ⇝ S,d↦^μ_n box_ν b ∥ E ▷^μ_n d
(lam)  S ∥ E ▷^μ_n λx.e        ⇝ S,d↦^μ_n λx.e ∥ E ▷^μ_n d
(all six: d fresh)

Substitution. let is the only rule with no store effect at all — pure substitution:

(let) S ∥ E ▷^μ_n let x=b in e  ⇝  S ∥ E ▷^μ_n e[x:=b]

Access-splitting (elimination). app, unbox, case_l, case_r all share one mechanism, already verified concretely earlier in this document: the store entry is pattern-matched as μ1+μ2 — the split isn’t computed separately, it’s baked directly into the left side of the rule — and μ2 is exactly the machine’s own current mode (same superscript on both sides, ▷^μ2_n). “The access mode” is simply whatever mode this step of the machine happens to be running at, not something separately negotiated:

(app)    S,b↦^(μ1+μ2)_m λx.e,S' ∥ E ▷^μ2_n b c
           ⇝ S,b↦^μ1_m λx.e,S' ∥ E ▷^μ2_n e[x:=c]
(unbox)  S,b↦^(μ1+μ2)_m box_ν c,S' ∥ E ▷^μ2_n unbox_ν b
           ⇝ S,b↦^μ1_m box_ν c,S' ∥ E ▷^μ2_n c
(case_l) S,b↦^(μ1+μ2)_m inl c,S' ∥ E ▷^μ2_n case_μ2 b {inl x→e1; inr y→e2}
           ⇝ S,b↦^μ1_m inl c,S' ∥ E ▷^μ2_n e1[x:=c]
(case_r) S,b↦^(μ1+μ2)_m inr c,S' ∥ E ▷^μ2_n case_μ2 b {inl x→e1; inr y→e2}
           ⇝ S,b↦^μ1_m inr c,S' ∥ E ▷^μ2_n e2[y:=c]

In all four, b’s binding is not consumed — it’s downgraded from μ1+μ2 to just μ1, still bound to the same value, reusable for a future access if μ1 permits one. app mirrors Figure 2’s own APP rule (“ignores the mode of the closure”), which is exactly why μ2 — not the closure’s own mode — is what carries through unchanged to govern e[x:=c] afterward: the applied argument’s mode, not the function’s, is what’s actually in play at this step.

SPLIT — the SUB-rule-driven branch, already verified concretely earlier: accessing a pair at UNIQUE reclaims its storage as a space credit; at ALIASED, the pair stays put and a dummy null credit (itself permanently (MANY, ALIASED, GLOBAL) per the WF-BASE rule) is handed back instead, since nothing can be safely reclaimed if another reference might exist:

(split_unique)  S,b↦^(μ1+μ2)_m (c,d),S' ∥ E ▷^μ2_n let(x,y,z)=b in e
                  ⇝ S,b↦^μ2_m ♣,S' ∥ E ▷^μ2_n e[x:=b,y:=c,z:=d]
                  (μ2 = (_,UNIQUE,_))
(split_aliased) S,b↦^(μ1+μ2)_m (c,d),S' ∥ E ▷^μ2_n let(x,y,z)=b in e
                  ⇝ S,b↦^μ1_m (c,d),S' ∥ E ▷^μ2_n e[x:=null,y:=c,z:=d]
                  (μ2 = (_,ALIASED,_))

REUSE — overwrites a reclaimed space credit with a fresh pair, allocated at the current frame n and mode μ (not the credit’s own original frame m, which is simply discarded):

(reuse) S,b↦^μ1_m ♣,S' ∥ E ▷^μ_n reuse b with (c,d)
          ⇝ S,S',b↦^μ_n (c,d) ∥ E ▷^μ_n b

Regions. enter-region/leave-region are the only two rules that ever move the frame counter n at all — every other rule above leaves n completely untouched. Detailed with a worked example and diagram in the next subsection.

(enter_region) S ∥ E ▷^μ_n borrow x=b for y=e2 in e3
                 ⇝ S,copy(n+1,S,b,b') ∥
                    (borrow x=b for y=E in e3) ▷^μ_{n+1} e2[x:=b']
(leave_region)  S ∥ (borrow x=b for y=E in e3) ▷^μ_{n+1} c
                 ⇝ S−(n+1) ∥ E ▷^μ_n e3[x:=b,y:=c]

copy — the auxiliary deep-copy operation invoked by enter-region. Every fresh address it creates is tagged at the same destination frame n (the argument passed in, not b’s own frame, which copy never even references) and the same mode (MANY, ALIASED, LOCAL) unconditionally — MANY because it may be read from both e2 and the later e3-with-y, ALIASED because it’s deliberately a second, non-exclusive reference, LOCAL because that’s the one fact that makes purging it on leave-region provably safe. Copying stops early (no recursive copy(...) call) at anything already guaranteed aliased — an aliased box, a global box, or a lambda — since there’s nothing exclusive left in those to protect by copying further:

copy(n,S,b,b') =
  b'↦^(MANY,ALIASED,LOCAL) ()                      if b↦^μ_m () ∈ S
  copy(n,S,c,c'), b'↦^(MANY,ALIASED,LOCAL) inl c'   if b↦^μ_m inl c ∈ S
  copy(n,S,c,c'), b'↦^(MANY,ALIASED,LOCAL) inr c'   if b↦^μ_m inr c ∈ S
  copy(n,S,c,c'), copy(n,S,d,d'),
    b'↦^(MANY,ALIASED,LOCAL) (c',d')                if b↦^μ_m (c,d) ∈ S
  copy(n,S,c,c'), b'↦^(MANY,ALIASED,LOCAL) box_M c'  if b↦^μ_m box_M c ∈ S
  b'↦^(MANY,ALIASED,LOCAL) box_A c                   if b↦^μ_m box_A c ∈ S
  b'↦^(MANY,ALIASED,LOCAL) box_G c                   if b↦^μ_m box_G c ∈ S
  b'↦^(MANY,ALIASED,LOCAL) λx.e                      if b↦^μ_m λx.e ∈ S
